# 08｜セキュリティ・個人情報・美学研究としての限界

この章は重要です。**Webに公開できたこと**と、**安全に大勢へ使ってもらえること**、**卒論の実験データとして使えること**は別の問題です。

## 1. 現在できている安全対策
- 作品ID・点数・理由・時間などをPythonで入力検証している。
- DBでも主キー・外部キー・点数範囲の制約がある。
- Supabaseの秘密鍵をJavaScriptへ埋め込まない。
- RLSを有効化し、ブラウザ用の `anon` / `authenticated` に直接DBテーブル操作の権限を与えていない。
- 公開 `/api/stats` は集計値のみを返し、個々のUUIDや回答一覧は返さない。
- 同じブラウザIDと作品IDの組み合わせで2回保存しようとするとDB制約で拒否する。

## 2. 現在できていない対策
- **ユーザー本人の認証がない**。UUIDはブラウザが自作して送るので偽装可能。
- **IPごとのレート制限がない**。大量リクエストによるDB消費や集計の汚染を防げない。
- **Bot対策・CAPTCHAがない**。
- **管理者専用の回答確認・削除・エクスポート・バックアップ画面がない**。
- **正式な同意・説明・撤回・データ削除の仕組みがない**。
- **本番とテストでデータ保存先を完全に分離する運用は未整備**。
- **リクエスト元の権限確認なしにサーバーの強いDBキーで書き込む**ため、RLSだけで公開APIの不正利用を防げない。

### 実際に注意すべき構造
~~~text
閲覧者A → 誰でも呼べる /api/ratings → Python → 強い権限のSupabaseキー
閲覧者B → 誰でも呼べる /api/ratings → Python → 同じDB
自動送信プログラム → /api/ratings → Python → 同じDB
~~~
「秘密鍵がブラウザに見えない」ことは**必要条件**ですが、それだけで安全になるわけではありません。

## 3. 研究で使うための改善案（優先度順）
1. **利用者の同意と説明**：何を収集し、なぜ集め、いつ削除するかを明示。
2. **参加を制限**：招待コード、参加者ごとのトークンなど。秘密のコードを画面のJavaScriptへ固定しない。
3. **1人1回答の管理**：ブラウザのUUIDだけに頼らない。
4. **レート制限・Bot対策**：送信数やアクセス頻度を抑える。
5. **練習用と研究用のDBを分離**：テスト点数が結果に混ざらないようにする。
6. **監査・バックアップ**：SQLの変更履歴、研究データの保全方法を決める。
7. **管理者向け集計・エクスポート**：権限を確認してから実行できる機能。
8. **データの削除・撤回手順**：研究倫理に応じて用意する。

これらは**提案**であり、現行コードに実装済みという意味ではありません。

## 4. 「匿名」について
現状の匿名IDは `crypto.randomUUID()` で作り、ブラウザの `localStorage` とSupabase上の評価行に保存します。名前やメールアドレスを登録させないという意味では匿名的ですが、**参加者の識別子と時刻が保存されている**ため、あらゆる文脈で完全匿名と断言できるわけではありません。

- ブラウザの保存領域を消すとIDと自分の採点表示は失われる。
- 別端末・別ブラウザでは別IDになる。
- サーバー側に既存の記録は残る。
- 現行アプリには参加者自身がサーバー記録を削除する機能がない。

研究参加者への説明では、その点を正確に伝える必要があります。

## 5. このアプリが測定していること
現行のコードが直接記録しているのは：
- 0～100点の **最初の評価**
- 評価理由（任意のカテゴリ1件）
- 計測した経過時間
- 再評価の点数（任意）
- 2作品比較で選んだ方
- 参加者UUIDと記録時刻

このデータから**記述統計（何人が何点をつけたか）**を出すことはできます。

しかし、測定した事実だけから次のような主張はできません：
- 「人はAI作品を人間作品より必ず低く評価する」
- 「AIだと知らせたから点数が下がった」
- 「芸術の美しさは点数で完全に表せる」
- 「この50作品の平均が、AIアート一般への評価である」

## 6. なぜ「AI情報を表示して再評価」だけでは不十分？
たとえば最初75点、説明後65点だった場合、差は -10点。
しかし理由は複数考えられます。
- AIが制作したと知ったから
- 2回目の鑑賞だから
- 時間が経って別の部分に気づいたから
- 質問の仕方に影響されたから
- 実験をしているという意識で答えを変えたから

**研究として因果関係を調べるなら、対照群・無作為割付・提示条件の統制・事前仮説・統計計画**などが必要です。

現行版では、提示前後の実験条件を無作為に割り振っていません。再評価も任意です。「説明を見ない条件」があっても、参加者が自分で選べるため適切な対照群とは限りません。

## 7. 卒論で想定できる実験設計（将来案）
研究課題の例：
> 同一の画像で、「AIが制作」と提示する条件と「作者情報を提示しない」条件では、最初の美的評価が異なるか？

検討項目：
- 参加者をあらかじめ条件ごとに無作為割付する。
- 作品の提示順をランダム化する。
- 作品の正確な制作情報を記録し、偽情報を提示する場合は倫理的配慮・必要な説明を検討。
- カテゴリ、画風、作品数、実験環境などの交絡を減らす。
- 研究参加者の同意、撤回、データ管理を指導教員と相談。
- 分析の単位（参加者／作品）、欠測値、除外基準を事前に決める。

この章は実験の発想を示すもので、特定の大学の倫理審査を通過した設計ではありません。

## 8. テスト画像50枚の大きな注意
`sample_manifest.csv` の `source` 列には `AI-generated contact-sheet panel` と記載されています。50枚は**1枚のAI生成コンタクトシートから切り出した画像**であり、**50回独立に生成された作品ではありません**。

テストでの動作確認には便利ですが、独立した刺激作品として一般化した研究結果を出すには不適切になりえます。卒論本番では制作モデル・プロンプト・生成日・作者性・編集履歴・利用許諾・画像解像度を個別に記録し、刺激選定を組み直しましょう。

## 10. 公開ソースのライセンス
GitHub上でコードを公開することと、第三者が自由に改変・再配布・商用利用できるライセンスを付けることは別です。このリポジトリには現時点で `LICENSE` ファイルがありません。ライセンス条件を定める場合は、権利関係や画像の利用条件を確認してから明示してください。

## 11. 現状をまとめると
**動く研究用プロトタイプとしては有用。ただし、研究参加者を広く募集する前に、セキュリティと研究倫理の設計が必須**です。
